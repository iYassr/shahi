# On-device UI checks (XCUITest)

A small `xcodebuild`-driven harness for the things a phone shows and a stub
cannot: real scroll behaviour, pairing, relay reconnection, several computers.
It is the counterpart to `docs/verify-on-device.md` and to the Maestro flows in
`.maestro/` and `e2e/native/` — Maestro can see that a label is *visible*;
XCUITest can read an element's *frame* and drive precise gestures, which is
what a question about *where* you are needs.

It lives outside `mobile/ios/` on purpose: that directory is regenerated by
`expo prebuild`, so a test target added inside it is wiped on the next prebuild.
This project drives the **already-installed** app by bundle id
(`XCUIApplication(bundleIdentifier: "app.shahi.mobile")`), so it needs no host
app and no share of the Expo project.

## Everything runs against the recording fixture

Every test pairs with `e2e/hosted/server.ts`: an encrypted relay and a box in
one process, whose writes end at the recording stub. Nothing reaches herdr, a
real computer or a real transcript, and no camera, credentials or deployed
relay is needed. From the repository root, keep both running while the tests
do:

```sh
HOSTED_PORT=7572 bun e2e/hosted/server.ts
HOSTED_PORT=7672 HOSTED_FIXTURE_ID=second-computer bun e2e/hosted/server.ts
```

The hosted Playwright configs bind 7572 and 7672 too. To run beside them, start
the fixtures elsewhere and say where: `SHAHI_FIXTURE_PORT=… SHAHI_SECOND_FIXTURE_PORT=…
mobile/uitests/run.sh`. Each fixture also uses the port above its own.

Use a **dedicated simulator** with the current app installed (a development
build on Metro, or a Release build): the tests pair, sign out and revoke.

```sh
mobile/uitests/run.sh                       # generates the project and runs every test
RESULT_BUNDLE_PATH=build/smoke-2.xcresult \
  mobile/uitests/run.sh -only-testing:ShahiUITests/ReleaseSmokeTests
```

`run.sh` regenerates `ShahiUITests.xcodeproj` with `xcodegen` first — **always
regenerate after adding a `.swift` file**, or the new file is not compiled.
Use a new result bundle path on each run; Xcode refuses to overwrite one.

Tests do not depend on each other's order. `Fixture.swift` takes the app from
whatever state the previous test left — onboarding, the saved computers, an
unreachable computer, or a pane pushed over the tabs — to the one a test needs,
and re-pairs with a freshly reset fixture.

## `ReleaseSmokeTests`

Pairing confirmation, transcript content, scrolling away from the tail,
preserving reading mode across navigation, sending with the keyboard,
foreground resume, a forced relay disconnect, exactly two recorded writes, and
device revocation returning to onboarding. Because of that last step it signs
out of every saved computer first. This is a simulator check, not proof of
native push, camera scanning, or physical-device performance.

## `ComputerSwitchTests`

Two fixtures as two computers: switching both ways and after a relaunch,
silent network loss and a cold offline launch, switching away from an offline
computer, one live connection per computer, and a computer update that keeps
its pairing.

## `ReaderPlaceTests`

Proves reading mode keeps your place in the fixture's 140-message
conversation: scroll back up, then leaving the pane and returning (or glancing
at the raw screen and back) must not throw you to the newest message. The
signal is content-independent — the "Go to latest" pill is present exactly when
you are away from the tail — and the `message-long-<n>` ids let it check you
returned to the *same* message.

The negative control is real: setting the reader's `following`/`pendingRestore`
to the at-tail state (disabling `scrollMemory`) fails
`…AcrossLeavingThePane`, which is the load-bearing case. `…AcrossTheScreenToggle`
is held by the overlay design (the list is never unmounted on a toggle), so it
passes with or without the restore; it guards against a regression to unmounting.

These are **local** checks, run by hand the way `docs/verify-on-device.md` is;
nothing in CI boots a simulator.
